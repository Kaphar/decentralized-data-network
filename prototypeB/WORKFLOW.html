DDN Prototype B — Workflow

Decentralized Data Network: Rust Node + SolidJS Frontend

Overview

Prototype B implements a Local Gateway Model: a Rust node handles all P2P networking, cryptography, and storage, while a SolidJS frontend provides the user interface. The browser talks to the local node via HTTP/WebSocket.

User Workflow

Step 1: Identity & Startup

When the Rust node starts, it generates a random Ed25519 keypair. The public key is used as the user identity (via did:key-style CID derivation). The frontend fetches this identity via GET /api/identity. 

GET /api/identity
{"pubkey": "bafz..."}

Step 2: Create a Post (Sign + Submit)

The workflow for creating any record:

  1. Build payload: Frontend constructs {text, media: [{cid, mime, size}]}
  2. Sign: POST to POST /api/record/sign — node signs with its private key and returns a BaseRecord with id, type, author, prev, ts, payload, sig
  3. Submit: POST the signed record to POST /api/record — node verifies the signature and stores the record in the CAS
  4. Display: Wall is refreshed by calling GET /api/wall
POST /api/record/sign     → {id, type, author, payload, sig, ...}
POST /api/record          → {id} (accepted)
GET  /api/wall            → {posts: [BaseRecord, ...]}

Step 3: Upload Media

Files are stored as blobs in the Content-Addressed Store. The blob CID (sha256 hash) is included in post payloads. 

POST /api/blob  (raw bytes)
{"cid": "bafy..."}
GET  /api/blob/:cid
{"bytes"}

Step 4: Send Direct Message

DM messages are records with type="message" and a to field in the payload. The UI polls for messages between two identities. 

GET /api/dm?me=&other=
{"messages": [BaseRecord, ...]}

Step 5: Peer Sync

  1. Add peer: POST peer URL to POST /api/peers
  2. Sync: POST to POST /api/sync — node pulls records from all known peers
  3. Each fetched record is verified (signature check) before being stored
POST /api/peers      → {"added": "http://peer:3000"}
POST /api/sync       → {"added": 3}
GET  /api/peers      → {"peers": ["..."]}

Record Schema

All data entities (posts, messages, profiles, contacts) are signed JSON records:

{
  "id":      "bafy...sha256...",     // hash of canonical JSON
  "type":    "post | message | profile | contact",
  "author":  "did:key...",          // public key CID
  "prev":    "bafy...or null",     // author's previous record
  "ts":      1728900000,            // unix seconds
  "payload": { ... },               // entity-specific data
  "sig":     "base64..."            // Ed25519 signature over id
}

Payloads by Type

Storage Model

The Content-Addressed Store persists blobs and records to disk under DDN_DATA_DIR/blobs/ and DDN_DATA_DIR/records/. Content is addressed by sha256 hash. 

DDN_DATA_DIR/
├── blobs/
│   ├── bafyabc123...   ← blob content
│   └── bafydef456...
└── records/
    ├── bafyrec789...   ← JSON record (canonical form)
    └── bafyrec012...
